# グローバル開発ルール

## 対象範囲と安全性

- 通常の変更対象は、現在のGit worktreeとする。
- まとまった変更の前に、現在のGit statusと既存のdiffを確認する。
- 関係のない変更、および利用者による既存の変更を保持する。
- 明示的な依頼がない限り、現在のworktree外のファイルを変更しない。
- 明示的な依頼がない限り、commit、push、force-push、reset、clean、rebase、その他Git履歴を変更する操作を行わない。
- 明示的な依頼がない限り、`.env`などの秘密情報にアクセスしない。
- 明示的な依頼がない限り、システム全体のパッケージを導入せず、永続的な端末全体の設定を変更しない。

## Web調査

- 情報がバージョン依存、時点依存、不慣れ、またはローカルリポジトリだけでは確実に判断できない場合は、積極的にWeb検索を使う。
- ライブラリ、フレームワーク、プロトコル、API、OS、CLIツールでは、モデルの記憶だけに頼らず現行の文書を確認する。
- 公式文書、仕様、upstreamリポジトリ、リリースノート、その他の一次資料を優先する。
- websearchで関連する資料を見つけ、webfetchで一次資料を確認する。
- バージョン固有の文書を適用する前に、現在のリポジトリで使われているバージョンを確認する。
- リポジトリ内だけで確実に答えられる場合は、ローカルの情報を優先する。
- 権威ある資料が食い違う、または現行の挙動を確定できない場合は、推測せず不確実性を報告する。

## 実装

- 曖昧さが実装または設計に実質的な影響を与える場合は、変更前に簡潔な確認を求める。
- 関係のないリファクタリングより、最小限で焦点の絞れた変更を優先する。
- 具体的な理由がない限り、既存プロジェクトの慣行に従う。
- コードを変更した後に、diffを確認する。
- 実行可能な場合は、関連する既存のtest、linter、型検査、buildを行う。
- taskを通すためだけに、test、型検査、lint規則、security check、validationを黙って弱めない。

## 報告

- 変更内容を要約する。
- 実施した検証と、その成否を示す。
- Web調査が実装に実質的に影響した場合は、関連する文書または資料を示す。
- 未解決の問題または不確実性を明示する。
